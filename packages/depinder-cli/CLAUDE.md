# depinder-cli — agent notes

The `depinder` CLI (Nx project `depinder-cli`, tag `scope:client`). The monorepo-wide agreements
are in the root `CLAUDE.md`.

## Open item: Trivy ↔ Grype SBOM cross-compatibility (unverified)

**Status: open. Raised 2026-09-16. Nothing in the code or tests answers this yet.**

### What the code does today

`scanFile()` (`packages/depinder-cli/src/plugins/sbom/local-scan.ts:764`) runs **both** scanners on **every**
`*.cdx.json`, in parallel, regardless of which tool generated the file:

```ts
const [trivyJson, grypeJson] = await Promise.all([
    runScanner('trivy', bin, ['sbom', '--format', 'json', sbomFile], sbomFile),
    runScanner('grype', bin, [`sbom:${sbomFile}`, '-o', 'json'], sbomFile),
])
```

So Syft-generated SBOMs are already being handed to Trivy, and Trivy-generated ones to
Grype. **What is unverified is whether each tool actually reads the same set of
packages out of the other's output.**

### Why this is not obviously fine

The normalization helpers already document real shape differences between the two
generators — see `packageKeys()` (`local-scan.ts:100`) and `cyclonedx.ts`:

- Syft purls carry a `package-id` qualifier; Trivy's do not.
- Grype's `artifact.name` for Maven is the **bare artifactId**, not `groupId:artifactId`.
- Syft records the manifest per component as `syft:location:0:path`; Trivy's components
  carry no manifest path at all.
- Syft emits a two-level graph with no project anchor; Trivy emits one `application`
  node per manifest.

`packageKeys()` compensates for these *when matching findings back to dependencies*.
It says nothing about whether the **scanner** parsed the file the same way.

### The failure mode that makes this urgent

A scanner that parses the SBOM but recognises **zero** packages still exits 0 and emits
valid JSON. `scanFile()` then records:

```ts
record.trivy = trivy ? 'ok' : 'skipped'   // 'ok' — it parsed
record.findingEntries = 0                  // ...and found nothing
```

**`ok` with 0 findings is indistinguishable from a genuinely clean project.** A silent
format incompatibility would look exactly like good news, in both the logs and the CSVs.
The preflight banner does not catch this: it only checks that the binaries exist.

### What to actually measure

Not exit codes — **package counts**. The harness already exists:
`sbom-scan-provenance.json` (`PROVENANCE_FILE`, `local-scan.ts:638`) records
`packageKeys` and `findingEntries` per file per tool.

Take one repo, generate both SBOMs, and fill in the 2×2:

| SBOM generated by | Trivy reads N pkgs | Grype reads N pkgs |
|---|---|---|
| Syft    | ? | ? (current assumed-good path) |
| Trivy   | ? (current assumed-good path) | ? |

A cell materially below the SBOM's own component count means that combination is
**not** supported, and the pairing must either be blocked or warned about explicitly.
Also worth recording: whether the CycloneDX **spec version** differs between generators,
since that is the most likely root cause if a cell comes back empty.

### DB refresh — this half is ALREADY ANSWERED (recorded here so it is not re-asked)

`warmScannerDatabases()` (`local-scan.ts:715`) refreshes both DBs **once per process**,
before the first scan reads either:

- `trivy image --download-db-only` and `grype db update`, run **side by side**
  (`Promise.all`), memoised in `warmPromise`, awaited by every scan.
- Only for scanners that are both installed **and** selected via `--vuln-source`.
- A current DB makes it a no-op returning in milliseconds.
- **On failure it warns twice and continues against whatever DB is already on disk.**

It exists because both scanners update lazily *inside* the scan: with every SBOM scanned
at once, a dozen child processes fetched the same archive simultaneously and all failed,
leaving empty vulnerability columns behind one `Command failed` line per file.

DB build dates are read at preflight and written to provenance:

- **trivy** — `trivy --version --format json` → `VulnerabilityDB.Version` + `UpdatedAt`
- **grype** — version from `grype version -o json`, build date from a *separate*
  `grype db status -o json` call

Pinned reference pair: **trivy 0.72.0, grype 0.115.0** (`PINNED_SCANNER_VERSIONS`).
The pin is verified and recorded, never enforced — a mismatch warns, it does not fail.

**Gap worth noting while here:** there is **no staleness threshold** on either scanner DB.
A DB that is six months old, whose refresh failed, scans silently. Contrast the GitHub
advisory cache, which has an explicit `--github-max-age` (`DEFAULT_MAX_AGE_HOURS`).
