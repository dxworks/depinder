# Black Duck-shaped export matches the transformed reports, and `analyse` writes it

## Breaking: CycloneDX SBOMs are the only input

- Depinder no longer parses lockfiles or manifests. The npm/yarn, Maven/Gradle (`deptree.txt`), pip/pipenv, Composer, NuGet (nuget-inspector) and Gemfile.lock parsers are removed, and with them the `depinder/` results subfolder. Generate SBOMs with Syft or Trivy — a DepMiner run writes both — and point `analyse` at them.
- Files that are not CycloneDX SBOMs are ignored; one info line gives their count.
- The plugins are the `sbom-*` ones. The old plugin names and aliases select them: `-p java` (or `maven`, `gradle`) is `sbom-java`, `-p npm` (or `js`, `yarn`, ...) is `sbom-npm`, and so on for `ruby`/`gem`, `python`/`pip`, `php`/`composer`, `dotnet`/`nuget`. `update` takes the same names.
- The registry cache is unchanged: entries stay keyed `java:`, `npm:`, `ruby:`, `python:`, `php:`, `dotnet:`, `go:`, `rust:`, so an existing cache keeps serving. CSV and Black Duck file names and contents are the same as before for SBOM input.
- Removed dependencies: `snyk-nodejs-lockfile-parser`, `@snyk/dep-graph`, `@snyk/gemfile`, `@dxworks/nuget-inspector`, `toml`, `npm`, and the unused `tmp` and `node-html-parser`.

## Breaking: the MongoDB cache is removed

- The registry cache is the SQLite database only, `~/.dxw/depinder/cache/depinder.sqlite` (or `DEPINDER_CACHE_DB`), one per machine. `analyse` no longer switches to MongoDB when a `depinder-mongo` container is running.
- `depinder cache init`, `cache up` / `start` and `cache down` / `stop` are removed. `depinder cache` / `cache info` shows the SQLite path, size and row counts; `cache import <dir>` is unchanged. Files an earlier `cache init` left in `~/.dxw/depinder/cache/` (`docker-compose.yml`, `init-mongo.js`) are unused and can be deleted.
- `depinder update [updated_before] [plugins...]` now works on the SQLite cache: it re-fetches the `libs` rows last written before the date (default one month ago), with the same arguments as before.
- `MONGO_URI`, `MONGO_USER` and `MONGO_PASSWORD` are no longer read.
- Removed dependencies: `mongodb`, `mongoose`, and `copyfiles` (no assets left to copy).

## `export-blackduck` is gone; `analyse` does its job

- `depinder export-blackduck` is removed. `depinder analyse <folders...>` now sorts every file it finds by **content**: a CycloneDX SBOM whose `metadata.tools` credits Trivy, or one that credits Syft. File names and folder names decide nothing: a `*.cdx.json` is read by name, and any other `*.json` whose first bytes declare `"bomFormat": "CycloneDX"` is read too. An SBOM from any other tool, or a `*.cdx.json` that is not CycloneDX, is named in a warning and skipped.
- The results folder gains one subfolder per source found: `trivy/` and `syft/` each hold exactly what `export-blackduck` wrote for that input alone (the `sbom-*` CSV triples, `sbom-scan-provenance.json`, `security.csv` and the seven other Black Duck-shaped files). A subfolder appears only when its source had input.
- `--project-name` and `--target` moved to `analyse`. The default project name is the SBOMs' shared repository name, else the input folder's name. The repository name comes from the SBOM's `metadata.component.name`, which both tools fill with the scanned directory's name, and falls back to the file name; the projects in `sbom-<eco>-libs.csv` are named the same way.
- The same repository twice from one producer is analysed twice and warned about. Trivy and Syft SBOMs of the same repository in one folder are fine: they go to different subfolders.
- `sbom-scan-provenance.json` now records, per SBOM, which tool wrote it and at which version, and lists only the SBOMs of its subfolder.
- One invocation opens the registry cache once and runs the scanner preflight once, however many sources it finds.

## The Black Duck-shaped files match the transform

- The SBOM export now writes `_dependencies.csv`, `_dependencies_sources.csv` and `_upgrade_guidance.csv` with the exact header line and cell conventions `transformBlackDuckReports` produces, and adds `_vulnerability_details.csv` (the transform's 23-column view of `security.csv`). A downstream reader processes a depinder folder and a transformed Black Duck folder the same way.
- Headers and cell rules moved to one shared module, `src/blackduck/columns.ts`, imported by both commands.
- Cell conventions in the shareable files: `Match type` is `Direct` / `Transitive` / `Direct,Transitive`; a zero per-severity count is blank while `Total` (every finding, the same count as libs.csv and the upgrade guidance) and `Critical and High` stay numeric; dates are `\tYYYY-MM-DD`; `Version id` is empty; `VerifiedPathMethod` is `not-checked`; files end with a newline.
- `1Component name` and `ProjectPathExists` are gone; `Version id` and `VerifiedPathMethod` are in.
- `Newer Versions (semver)` left the Black Duck-shaped files for the new depinder-only `_component_versions.csv`.
- `addCategoriesToBlackDuckReports` joins on `Component Version Origin Id` when every `Version id` is empty and reads the repository from `ProjectPath` when no `VerifiedPath` was verified, so it works on an `analyse` SBOM subfolder.
- `security.csv` is unchanged.
